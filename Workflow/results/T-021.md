## Q3. Live 真正有多少"文字绘制宽度"（AppCellView.swift:291-310）

配置：`NSTextField(labelWithString:)`，alignment .center，font 10，byTruncatingTail，maxLines 1，frame 宽 104pt。

**probe2/probe5（AppKit 独立实测，cacheDisplay 离屏渲染 + 像素 extent）**：

| API | 返回值 |
|---|---|
| `label.bounds` / `label.frame` | (0, 0, **104**, 13) |
| `label.cell?.drawingRect(forBounds:)` | (0, 0, **104**, 13) |
| `label.cell?.titleRect(forBounds:)` | (0, 0, **104**, 13) |
| `label.cell?.cellSize(forBounds:)` | (101.83, 13) |
| **实际渲染可见宽**（"Adobe Photoshop 2026" @104） | **93.5pt**（"Adobe Photoshop…"，居中） |
| 全名渲染宽 | 113.5pt |

**关键：公共 API 全部报 104pt，但 cell 实际截断宽度 ≈ 96.3pt（frame − 7.7）**。边界实测（probe4/probe8，@104pt frame）：

| 名字 | typo 宽 | live 可见 | 判定 |
|---|---|---|---|
| GarageBand 10.4.12 | 95.77 | 95.0（=全名） | full → 有效宽 ≥ 95.77 |
| Audio MIDI SetupXX | 96.83 | 91.0 | TRUNCATED → 有效宽 < 96.83 |
| Digital Color MeterX | 97.49 | 94.0 | TRUNCATED |
| Affinity Designer 2.6 | 98.72 | 88.0 | TRUNCATED |

→ **live 有效截断宽度 ∈ [95.77, 96.83) ≈ 96.3pt**。多 frame 扫描（90/96/104/120）一致满足 `W_t = frame − 7.5~7.7`；高度无关（13/20/30pt 同结果）；shadow 不影响截断（只扩展模糊像素）；NSAttributedString 直接绘制路径截断在 ~100.5-103pt（无 7.5pt 内缩）→ **该内缩是 NSTextFieldCell 私有绘制行为，公共 API 不可复现、不可查询**。

### Case 判定：**Case A**（raw PageVisual PNG 已正确省略号 → Renderer 的截断实现本身没问题）

但 Case A 分支的"查旧 cache"**不是根因**：PageVisualCache 是内存缓存（PageVisualCache.swift），几何/显示修订/重启即失效重建，v0.7.1 重启后必然用新渲染器。真正的根因在 Q3 的宽度契约：

### 根因结论：**live/raster effective width contract 不一致（Case B-YES 分支的结论）**

- raster 截断宽度 = labelRect.width = **104pt**（cellSize−4，与 live 约束同源）
- live 实际截断宽度 = **~96.3pt**（frame−7.7，NSTextFieldCell 私有内缩，公共 API 不可见）
- 差 **~7.7pt**。后果：
  - typo 宽 ∈ (96.3, 104] 的名字（如 "Affinity Designer 2.6" 98.72pt）：**raster 显示全名，live 显示省略号** → 滑动（compositor 显示 PageVisual）时用户看到"全名"，静止时看到省略号 —— 与用户反馈"滑动时仍显示全名"完全吻合
  - typo 宽 > 104 的名字（如 "Adobe Photoshop 2026" 113.8pt）：raster 截到 101.16pt（"Adobe Photoshop 20…"），live 截到 93.5pt（"Adobe Photoshop…"）→ 滑动时多 1-2 个字符 —— 与"更多字"吻合
- T-019 修复本身**有效且正确**（raster 现在确实截断，红态复跑结论成立）；它修的是"raster 不截断"，但没修"raster 与 live 截断宽度不同"

## 修复建议（供 Chief 决策，未实施）

1. **首选（任务 §5 优先方案）**：让 raster 使用 live 的有效宽度 —— `drawLabel` 中截断宽度改为 `labelRect.width − 7.5`（≈ cellSize − 11.5），**保持 labelRect 与居中不变**（live 的截断行也是在整个 104pt frame 内居中，probe6 验证：raster @96.5 截断 → 94.0pt 居中 ≈ live 93.5pt）。不改 live NSTextFieldField 行为。
   - 注意：7.5 是经验值（font 10pt 下实测 [95.77, 96.83) 区间），建议以常量 + 注释 + 回归测试固化，或运行时从 live cell 实测一次（渲染二分）后传入；**不要**用 `titleRect/drawingRect` 查询（实测两者都报 104，不反映真实宽度）。
2. **验证方法**：修复后 `pagevisual_longname_2x.png` 标签带可见宽应从 100.0pt 降到 ~93.5-94pt（与 live 一致）；`pagevisual_affinity_2x.png` 应从全名变为省略号。
3. **缓存键影响**：若截断宽度由 cellSize 派生（cellSize−11.5），PageVisualKey 的 geometry 签名不变，无需改键；若改为独立实测值，需并入签名（影响面大，不推荐）。
4. **次要检查**（Case A 分支残留）：确认用户实测时 app 已重启（内存 cache 无旧代残留）；`--disable-pagecompositor` 下无此问题（live 直绘），可作 A/B 佐证。

## 勘误注记（2026-08-27，Main 追加，Chief 决策）

- **错误假设**：Q4 中"CTLineCreateTruncatedLine 恒附省略号"**不成立** —— probe5 的 101.16pt 实为**硬切宽度**（无省略号字形）。本机 macOS 26.5 SDK 实测：nil token 从不附加省略号（"Affinity Designer 2.6"@96.5 → "Affinity Designer 2." 92.24pt）。
- **影响**：该假设被写进 T-022 任务文本（"省略号"预期），T-022 Reviewer 发现 raster 硬切 vs live 真省略号（MAJOR）。
- **处置**：Chief 决策采纳显式 "…" token（T-023 交付省略号对齐）；7.5 常量无需重校准（width 参数=结果行总宽上限含 token，与 live 同构）。
- **教训**：probe 结论需区分"实测值"与"推断假设"；CTLineCreateTruncatedLine 的 token 行为应实测而非假设。
